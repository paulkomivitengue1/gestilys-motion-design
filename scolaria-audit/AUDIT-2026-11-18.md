## Bugs et risques — sécurité (critiques)

### C1 — Un utilisateur d'école peut modifier son propre abonnement (CODE ; BASE RÉELLE à vérifier)
- **Module :** base de données, table `schools`.
- **Fichier :** `supabase/migrations/20260801094155_create_multi_tenant_schema.sql`, politique `update_own_school` (`FOR UPDATE TO authenticated USING/WITH CHECK id = current_school_id()`), sans restriction de colonnes.
- **Constat :** aucune migration ultérieure n'ajoute de garde sur les colonnes d'abonnement (recherche des triggers sur `schools` : seuls commissions, journal de statut et durée d'essai à l'insertion). Le client n'utilise l'UPDATE direct que pour `name` (`db.ts` → `updateSchoolName`).
- **Reproduction (théorique, non exécutée) :** connecté en tant qu'utilisateur d'une école, appeler `supabase.from('schools').update({ subscription_status: 'active', plan: 'Élite', trial_ends_at: '2099-12-31' }).eq('id', <son id>)`.
- **Conséquences possibles :** forfait payant gratuit, levée d'une suspension posée par l'admin (`20261017091500_admin_school_status_controls.sql`), et commission d'affiliation déclenchée (trigger « statut → active ») si `referred_by_code` est renseigné.
- **Correction proposée :** trigger `BEFORE UPDATE` bloquant ces colonnes pour les rôles `authenticated`/`anon` (fichier `proposed/20261118000000_protect_billing_columns.sql`). **Non testée.**

### C2 — Un utilisateur d'école peut fabriquer ou modifier des paiements (CODE ; BASE RÉELLE à vérifier)
- **Module :** table `manual_payments`.
- **Fichier :** `supabase/migrations/20260815223448_add_manual_payments_rls_policies.sql` (policies SELECT/INSERT/UPDATE/DELETE limitées à l'école, sans restriction de `status` ni de colonnes).
- **Conséquence possible :** insertion d'un paiement déjà « valide » ou changement de statut/montant : chiffres du panneau admin faux (revenus, MRR), validation contournée.
- **Correction proposée :** trigger imposant `status = 'en_attente'` à l'insertion cliente et interdisant UPDATE/DELETE client sur un paiement traité. **Non testée.** À confirmer : le flux légitime de l'école ne doit pas modifier un paiement après création.

### H1 — Connexion admin : requête envoyée à chaque touche (CODE)
- **Module :** panneau admin, écran de connexion. **Fichier :** `src/components/AdminPanel.tsx`.
- **Constat :** le champ du code est lié à l'état `code`, et un `useEffect([code])` appelle `setAuthed(true)` puis `loadData(code)` dès qu'il est non vide. Chaque caractère tapé déclenche donc un appel au serveur avec un code partiel, l'interface bascule entre connexion et panneau, et chaque échec efface la session.
- **Reproduction :** ouvrir l'admin, saisir un caractère dans le champ du code, observer les requêtes réseau et le clignotement.
- **Correction :** séparer l'état de saisie de l'état validé, ne charger qu'à la soumission.

### H2 — Durcissement de la fonction admin (CODE)
- **Fichier :** `supabase/functions/scolaria-admin/index.ts`.
- (a) L'e-mail pris dans le jeton retombe sur la charge utile non vérifiée si `getUser` échoue : sans danger uniquement si `verify_jwt` est actif (aucun `config.toml` dans le dépôt pour le prouver) — BASE RÉELLE à vérifier.
- (b) Le code admin est comparé par `===` (non constant-time) et sans limitation de tentatives.
- (c) Les actions publiques (`record_visit`) renvoient le message d'erreur brut de la base.
- **Correction :** comparaison constante, plafond d'échecs par IP/e-mail, message générique, refus si e-mail non vérifié.

### H3 — Validation d'un paiement non idempotente (CODE ; migrations ultérieures à contrôler)
- **Fichier :** `20260803191644_add_admin_panel_tables.sql.sql`, fonction `admin_validate_payment` : pas de contrôle du statut courant ; valider deux fois prolonge deux fois l'abonnement et compte deux fois le revenu. Idem pour `set_school_paid_status(paid=true)` dans la fonction admin (insère un paiement à chaque appel).
